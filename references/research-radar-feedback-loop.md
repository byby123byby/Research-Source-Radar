# 中文研究雷达反馈闭环

这个闭环解决的不是“来源是否真实”本身，而是：用户希望一次研究发现能带来原本不知道、但可能真正推动项目的论文、开源项目和方法。它将主动发现、人工价值判断和下一轮调整连在一起；来源身份核验仍在后台保留，不能被偏好绕过。

## 对用户的单次体验

用户只调用 Research Source Radar，并用中文获得四组候选：

- **优先看**：很可能改变当前架构、算法、实验或研究问题的来源；
- **热门前沿**：近期活跃或被多类独立技术来源讨论的候选，热度不等于有效；
- **跨域启发**：来自不同学科或生态、但有明确机制桥接的候选；
- **持续关注**：目前证据、适配或时机不足，但值得以后重新检查的来源。

发现阶段可以保留较大的元数据候选池；向用户呈现时不应假装所有候选已被深入验证。每张候选卡都写明它是什么、为何此刻推荐、可迁移机制、热度或时效依据、来源链接，以及“值得深入看/可借鉴机制/暂时没用/已经知道/不想再推荐这类/不确定”的人工标签。

来源链接是候选卡的必填项，必须直接贴出可打开的权威来源或稳定标识符。没有真实链接的候选不能进入主列表；只能记录到“未核实/遗漏”并说明失败原因。不能用来源名称、搜索关键词或“请自行搜索”代替链接。

评审者可以使用这些固定标签，也可以写自然中文。`extract-review` 会保留原始标注和理由，并先生成可检查提案：明确的“可借鉴机制”仍是正向反馈；原始标注中含“可能”“不知道”或“可以看看”时保守归为“不确定”，即使同一句里出现“迁移”；理由里的“一般般”只会降低到“不确定”，而原始标注明确写“很一般”“没有那么想要”或“当前不需要”才会降为“暂时没用”。提案在写回画像前必须可读、可检查，不能把模糊感受伪装成强偏好。

## 明确反馈，而不是隐藏画像

偏好记录只能来自用户明确给出的标签、原因和机制标签。保存位置由用户选择，例如目标项目下的 `.research-source-radar/profile.zh-CN.json`。记录必须可读、可导出、可修改和可清空；不读取社交平台浏览历史，不把反馈上传给外部模型，也不把单次反应伪装成模型训练。  
**分数、排名、价值判断全部由用户人工确认；Skill 不生成“价值分数”或“自动判断可迁移强弱”。**

相关性和投入优先级必须分开。建议使用三层注意力状态：`deep_priority`（明确值得深入、夯、多推荐、好好看看或值得迁移）、`mechanism_reference`（明确可借鉴机制但没有强深挖信号）、`light_reference`（相关、可以看看、值得看看、一般般但可参考，或明确不建议重点投入）。模型不得因为候选进入正向候选池，就平均提高所有候选的深挖优先级。

### 1-n 个用户示例与偏好假设

用户可以一次贴 1-n 个自己认为相关的论文、项目、数据集、截图或模糊名称。Skill 应按以下顺序处理：

1. 逐个定位真实来源、版本和来源类型；无法确认的示例保留为未核实锚点，不用标题猜偏好。
2. 建立来源特征表：研究问题、机制、输入/输出、数据、评测、证据深度、部署边界、时间和用户明确理由。
3. 分离共同机制、偶然共同点和来源之间的差异；不得把共享关键词直接当成偏好。
4. 输出可见的“偏好假设”：假设内容、支持它的示例、证据强度、反例和待确认部分。
5. 用确认陈述和标注为临时的假设扩展查询、安排候选顺序；示例本身不计入新发现。

偏好假设的置信度应随示例数量和解释一致性变化：一个示例只能形成暂定假设；多个示例若共享具体机制并且理由一致，才可以提高为较强的当前任务假设。即使如此，也不能自动写入全局画像；只有用户明确确认，才允许导出为项目偏好。

示例输出：

```text
偏好假设 H1：你可能更看重“可迁移的机制和评测方法”，而不是能直接安装的完整产品。
证据：示例 S1、S2 都公开了机制/评测细节；这是来源观察与用户示例共同支持的临时假设。
反例：S3 更偏直接部署，尚不能判断你是否也重视部署便利。
当前作用：扩大机制邻居查询并提高其展示顺序；不写入全局偏好。
```

评审卡可以同时支持正式标签和有顺序的口语标签：`夯 > 顶级 > 人上人 > NPC > 拉完了`。其中 `夯/顶级`对应“值得深入看”，`人上人`对应“可借鉴机制”，`NPC`对应“相关但仅作参考”，`拉完了`对应“暂时没用”；`避雷`对应“不想再推荐这类”。口语标签只是输入别名，画像中仍保存用户原话、规范化标签和理由；“拉完了”只影响当前候选，不能自动拉黑其所有机制标签。

### 结果后的自然反馈

用户可能不会逐条打分，而是说“你推荐的整体一般般”。此时按范围处理：

- “这个来源一般般”：只降低该候选为 `light_reference`，不拉黑它的全部机制标签。
- “这一批整体一般般”：记录为本轮结果质量信号，不写入长期偏好画像。
- “一般般，因为太泛/太具体/没有机制/不能推动项目”：把原因转成下一轮检索诊断，分别减少泛主题结果、增加机制邻居、验证/失败来源或项目桥接。
- “一般般但这个机制可以借鉴”：记录为 `mechanism_reference`，不升级为 `deep_priority`。
- 没有原因时：只有在原因会改变下一轮路线时才追问一个短问题；不得自行猜测用户讨厌整类来源。

如果用户表达的是“这次推荐的都不是我想要的”，这不是普通的候选降权，而是一次检索失败反馈。Skill 可以在恢复搜索前问最多两个短问题，但不能让用户重新填写完整需求表。优先问“你更想要机制、可落地实现、数据/指标、验证方法还是跨域迁移？”以及“这次最不想看到哪类结果？”然后：

- 保留本轮候选、已核验来源和用户不满意的原话；
- 检查是否搜错了问题范围、术语、来源生态、机制桥接、时间窗口或可行动性；
- 自动切换到不同的恢复路径，例如从问题直连改到机制邻居、失败/验证来源、领域原生注册库或长尾实现；
- 将第二次结果与第一次结果的搜索方向变化写出来；
- 将用户的新回答与当前项目已经明确确认的偏好合并使用，并在结果中说明实际采用了哪些偏好；
- 如果用户没有回答，使用当前上下文中最保守的解释继续搜索，并明确说明假设；
- 不把“这次没找到想要的”记成“用户不喜欢这一整类来源”。

下一轮应向用户展示“原话 -> 系统记录 -> 影响范围”，例如：

```text
原话：这批推荐一般般，感觉比较泛。
系统记录：本轮结果质量反馈；减少泛主题直连结果，增加机制邻居、验证/失败和具体实现来源。
不会记录：用户不喜欢所有相关论文，也不会拉黑某个机制标签。
```

### 项目隔离

Research Source Radar 是跨学科 Skill，不是某个项目的推荐器。一份画像只服务其 `project.name`、研究问题和约束；默认不得自动读取、合并或迁移另一项目的标签。新论文、实验、产品、政策分析、人文研究或艺术实践都应新建独立画像。只有用户显式导出、比较或复制某些标签时，才允许跨项目使用，并必须在输出中标明这些标签来自哪个原项目。这样一个 iOS 项目对“端侧、低延迟”的偏好不会污染金融、生命科学、历史、设计或其他研究任务。

下一轮可以使用已确认的正向标签扩大机制和关联网络，也可以降低用户明确不想重复的特征。负向标签只影响排序，不能让尚未核验的新方向永久消失。默认保留至少 20% 探索候选：一部分来自热门/近期生态，一部分来自机制或跨域邻居。

`暂时没用` 是候选级判断：它只记录“此来源目前不适合这个项目”，不能自动把该候选的所有机制标签列为禁区。只有用户明确选择 `不想再推荐这类`，系统才会把用户写出的机制标签用于降低相似候选的排序。这样一次对某个 Android 基准、旧模型或重型框架的否定，不会误伤截图、记忆、评测等仍可能有价值的研究方向。

## 排序规则

排序必须逐项解释，而不是输出黑箱总分：

1. 当前项目推进潜力：能否改变架构、算法、实验、成本、延迟或研究边界；
2. 与当前问题及明确偏好的机制桥接；
3. 新鲜度与多源注意信号；
4. 来源身份和证据状态；
5. 直接部署或机制迁移的成本与冲突。

热门是一个与问题检索并列的**主候选入口**，但不会替代机制、失败、验证和跨域路径。热门候选先进入候选池，之后仍须通过身份、相关性和风险检查。

## 人工评估

不要让模型声称“这组来源更有价值”。评估时将不同策略的候选卡去除策略名称后混排，由用户标注。主要指标是 `user_approved_novel@k`：用户此前不知道、并明确认为值得深入看或可借鉴机制的候选数。另行报告 `deep_priority_rate` 和 `light_reference_rate`，因为“相关”不等于“值得平均深入”。`already_known`、`not_useful_now`、`avoid_similar` 和 `uncertain` 保留为同样重要的反馈，不计为成功。

## 本地工具

`scripts/radar_feedback.py` 提供五个不联网命令：

```bash
# 1. 建立可见的中文项目画像
python3 scripts/radar_feedback.py init \
  --output .research-source-radar/profile.zh-CN.json \
  --project-name "项目名称" \
  --description "当前研究目标" \
  --constraint "实际约束"

# 2. 将候选 JSON 渲染成中文评审卡
python3 scripts/radar_feedback.py render-review \
  --profile .research-source-radar/profile.zh-CN.json \
  --candidates candidates.json \
  --output review.md

# 3. 根据模板记录人工标签
python3 scripts/radar_feedback.py record-feedback \
  --profile .research-source-radar/profile.zh-CN.json \
  --feedback references/radar-feedback-template.zh-CN.json

# 3a. 从填写过的中文评审卡生成可检查提案，再确认写入
python3 scripts/radar_feedback.py extract-review \
  --review review.md \
  --candidates candidates.json \
  --output feedback-proposal.json
python3 scripts/radar_feedback.py record-feedback \
  --profile .research-source-radar/profile.zh-CN.json \
  --feedback feedback-proposal.json

# 3b. 若发现旧导入错误，归档旧画像后替换，绝不静默覆盖
python3 scripts/radar_feedback.py replace-feedback \
  --profile .research-source-radar/profile.zh-CN.json \
  --feedback corrected-feedback.json \
  --archive .research-source-radar/profile-before-correction.json

# 3c. 升级规则后，只重算导出提示，不修改原始人工反馈
python3 scripts/radar_feedback.py refresh-guidance \
  --profile .research-source-radar/profile.zh-CN.json

# 4. 查看下一轮检索要遵循的中文提示
python3 scripts/radar_feedback.py show-guidance \
  --profile .research-source-radar/profile.zh-CN.json
```

工具不会自行抓取网页或替你判断项目有价值；它只保存你的明确判断并生成下一轮 Radar 可见的中文检索提示。
