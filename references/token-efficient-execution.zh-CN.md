# Token 高效执行规则

这份规则用于减少重复上下文、重复检索和不必要的深读，同时保留问题直连、机制邻居、跨域迁移、近期热点和长尾来源的覆盖。它是可选执行策略，不要求安装第三方库，也不能替代真实来源核验。

## 1. 先缓存可复用事实，不缓存模糊结论

为每次检索建立请求指纹，至少包含：

- 规范化后的任务目标和约束
- 显式给出的论文、仓库、模型、截图或线索
- 项目画像的本地标识
- 截止日期、来源类型和当前工具/模型

只在这些条件一致时复用已核验的来源卡。若截止日期、项目画像、工具、模型或任务约束改变，必须重新核验。缓存中保留 canonical URL、来源身份、版本/日期、核验时间和证据，不把旧的相关性判断冒充新的用户偏好。

优先使用精确缓存；语义缓存只能用于发现相似查询或减少重复查询，不能直接替代来源身份核验。若需要语义缓存，可参考 MIT 许可的 [GPTCache](https://github.com/zilliztech/GPTCache)，但它的 README 明确提示 API 仍可能变化，因此不要把它作为本 Skill 的硬依赖。

## 2. 把便宜步骤和高风险步骤分开

可以交给较便宜的模型或本地规则的步骤：

- 查询规范化、同义词展开和候选去重
- URL/标题格式整理
- 已核验来源卡的压缩和排序草稿
- 输出 schema 检查

必须保留强核验或强模型预算的步骤：

- 论文、仓库、数据集、标准或政策来源的身份核验
- 论文/README/代码/配置/评测/限制的重点阅读
- 来源到目标的机制映射和迁移完整性门禁
- 医疗、法律、金融等高风险结论
- 最终遗漏风险和未迁移项说明

可参考 Apache-2.0 许可的 [RouteLLM](https://github.com/lm-sys/RouteLLM) 的强/弱模型路由思想，但不要直接采用其默认阈值。若启用路由，必须用本项目自己的跨学科任务和用户反馈校准，并记录强模型比例、质量变化和失败案例。

## 3. 只压缩重复上下文，不压缩证据

允许压缩：

- 多轮调用中重复出现的任务说明
- 已经核验过的长 README/摘要中的非关键背景
- 重复的候选解释和相同查询结果

必须原样保留或生成短而完整的证据摘要：

- 标题、canonical URL、DOI、仓库路径
- 发表/发布/版本日期
- 关键机制、前提、状态变量和更新规则
- 评测方法、结果、限制和失败处理
- 来源到目标的映射、冲突和未迁移项
- 用户原话、项目画像边界和 source_ref

如果用户安装了 MIT 许可的 [LLMLingua](https://github.com/microsoft/LLMLingua)，可以只对重复上下文做可逆前的压缩试验。每次压缩必须记录压缩前后 token 数，并抽查标题、日期、限制、URL 和覆盖矩阵是否仍在。LLMLingua 项目给出了较高压缩率的实验结果，但本 Skill 不把该结果当作所有任务都能保持质量的保证。

## 4. 分阶段深读，不能平均深入所有候选

推荐采用以下预算顺序：

1. 广泛发现：每条候选只生成短来源卡，保持不同路线和来源生态的配额。
2. 轻量整理：去重、合并同一来源的不同入口，保留版本差异。
3. 分层深读：优先读直接匹配和高机制价值来源，同时强制保留少量机制邻居、跨域和长尾名额。
4. 完整性门禁：对最终少数来源阅读原始来源并检查组件/主张清单、映射、测试证据和未迁移项。

不得因为压缩或缓存而取消长尾配额，也不得只深读热度最高的来源。

## 5. 每次执行报告节省了什么

最终报告至少记录：

- 总调用数、缓存命中数和缓存未命中数
- 输入/输出 token 或可用的近似 token 统计
- 压缩前后 token 数和压缩比例
- 被去重的候选及其保留理由
- 被延后深读的候选
- 因预算未核验的来源和遗漏风险

如果无法测量 token 节省，就只能称为“预算策略”，不能宣称已经节省 token。任何节省都必须与来源真实性、机制覆盖、迁移完整性和用户认可的新发现一起评估。

## 6. 本 Skill 的默认策略

默认不安装、不调用上述第三方项目。Skill 先使用自身的请求指纹、短来源卡、分阶段深读和证据保留规则；只有运行环境明确提供可选组件时，才启用对应适配。可选组件失效时必须退回普通流程，不能减少来源覆盖，也不能跳过核验。
